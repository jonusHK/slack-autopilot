## D-001 엔진·정책 분리 — 엔진은 범용, 정책은 대상 레포의 `AUTOMATION.md`

- **문제**: 첫 소비자 외에 다른 프로젝트 자동화가 예정돼 있다. 한 프로젝트 전용으로 만들면
  나중에 범용화 추출 비용을 치른다. 반대로 엔진이 프로젝트 사정을 알기 시작하면 분리가
  무의미해진다.
- **결정**:
  - **① 엔진(이 레포)은 프로젝트 지식이 필요 없는 것만** — 상태 기계, 검출·클레임, 락·멱등성,
    자기 수정 루프, 순차 병합, Slack Web API 래퍼, 채널↔레포 매핑 설정.
  - **② 판단 기준은 대상 레포의 `AUTOMATION.md`** — 티어 A/B 경계, CI 워크플로 이름, 필수
    리뷰어, 병합 금지선, 재번호 규칙, 결정 기록 규칙. 계약은 `design/policy-contract.md`.
  - **③ 정책 파일이 없는 레포는 처리하지 않는다** — 검출된 전 항목에 ❓. 정책 없는 자동
    구현이 가장 위험한 형태라, "붙이는 걸 깜빡한 프로젝트"가 조용히 자동화되는 일을
    구조적으로 막는다.
  - **④ 회귀 테스트**: 두 번째 프로젝트를 붙일 때 필요한 것이 `AUTOMATION.md` 작성 + 엔진
    설정 한 줄을 넘으면 분리가 샌 것이다 — 엔진에 새어든 프로젝트 지식을 찾아 정책으로 옮긴다.
- **이유**: 정책이 대상 레포에 살아야 그 레포의 규칙 문서·가드와 **같은 커밋에서 진화**한다.
  분류 오판의 수선 지점도 엔진이 아니라 그 프로젝트의 정책 파일이 된다.
- **연결**: `design/policy-contract.md`(정책 파일 계약).

## D-002 이모지 상태 기계 — ▶️·🚀 는 사람 전용, 봇 자기 트리거 금지

- **결정**: 작업 노드(메시지/스레드 답글)의 상태는 이모지가 전부다. ▶️(진행 지시)와
  🚀(병합 지시)는 **사람만** 붙이고, 봇은 어떤 경로로도 이 둘을 붙이지 않는다. 봇이 붙이는
  것은 💬(클레임)·📬(PR 생성)·❓(판단 대기)·✅(병합 완료)·❌(실패)뿐.
- **이유**: 봇의 트리거 이모지를 봇이 만들 수 있으면 자기 재귀(자기 답글에 ▶️ → 자기가
  집음)가 가능해진다. 금지 목록 한 줄이 무한 루프를 구조적으로 불가능하게 만든다.
  이모지는 사람이 보는 표시이고, 기계의 락은 원격 브랜치다(engine.md §3).
- **상태 정의는 engine.md §1** — 이 결정은 "누가 붙이는가"의 불변식만 고정한다.

## D-003 실행 표면 — 클라우드 루틴 + 대상 레포 CI

- **결정**:
  - **① 루틴은 Claude Code 클라우드 루틴**(cron 스케줄, 매시). 사람의 로컬 머신에서 아무것도
    돌지 않는다.
  - **② 무거운 검증(테스트·e2e)은 대상 레포의 GitHub Actions 가 한다** — 엔진은 PR 을 열고
    CI 결과를 읽을 뿐, VM 에서 docker·DB 를 띄우지 않는다.
  - **③ 슬랙 접근은 봇 토큰 + Web API 로만** — claude.ai 커넥터(MCP)는 클라우드/headless
    런에 없을 수 있으므로 의존 금지.
  - **④ 상태를 루틴의 기억에 두지 않는다** — 루틴은 매 실행이 새 세션이다. 모든 상태는
    슬랙 이모지 + 원격 브랜치에 있고, 어느 실행이 죽어도 다음 실행이 같은 판정으로 이어간다.
- **기각한 대안**: 로컬(remote-control·launchd) — 병렬 워크트리가 개발 스택과 자원을 다투고
  remote-control 은 프로세스당 1세션이라 병렬과 상충. Slack 이벤트 → workflow_dispatch —
  수신 서버 운영이 필요해 솔로 운영에 과함(폴링이 운영 부담 0 으로 같은 결과).
  세션 내장 cron(CronCreate) — 세션 전용·7일 만료라 지속 루틴의 기반이 못 됨.

## D-004 검증 규율 — CI 그린까지 자기 수정, 상한 5회/60분

- **결정**: 빨간 PR 을 남기지 않는다. 에이전트가 CI 실패 로그를 읽고 스스로 고쳐 그린으로
  만든다. 상한은 **5회 시도 / 60분** — 초과 시 ❌ + 실패 요약 답글 후 정지.
- **그린으로 인정하지 않는 것 둘**:
  - **가드 우회** — 대상 레포의 pre-commit 가드를 `SKIP_*` 류로 넘기는 것. 가드를 끄는
    자동화는 가드를 없애는 것과 같다.
  - **테스트 약화** — 단언 삭제·skip 으로 통과시키는 것. 이 경우는 ❌ 로 낸다.
- **이유**: 무제한 재시도는 같은 실패를 반복하며 토큰만 태운다. 60분이면 사람이 볼 수 있는
  다음 사이클과 만난다.

## D-005 병합은 사람 🚀 게이트 후 순차 — 자동 병합 없음

- **결정**: CI 가 그린이어도 사람이 PR 링크 답글에 🚀 를 달기 전에는 병합하지 않는다.
  병합 루틴은 🚀 있고 ✅ 없는 것만 집어 **순차** 처리하고, 완료 시 ✅ + 충돌 해소 기록을
  답글로 남긴다.
- **이유**: 사람이 PR 내용을 읽는 지점이 자동화의 유일한 관문이다. 순차 병합이라 병렬 PR 의
  번호 충돌(마이그레이션·결정 로그 등 — 정책 파일의 재번호 규칙)이 병합 직전 재번호로 풀린다.
- **자동 병합 금지선**(❓ 로 사람에게): 로직 충돌(같은 함수 본문이 양쪽에서 변경), 정책
  파일이 지정한 금지선 파일의 충돌, 정책 파일이 지정한 민감 경로 변경이 diff 에 포함된 PR.

## D-006 스레드 답글 재투입 — ❓ 는 막다른 길이 아니라 대기열

- **결정**: 검출 대상("최근 7일 · ▶️ 있고 💬 없음")에서 **부모 메시지와 스레드 답글을
  구분하지 않는다**. 봇이 ❓ 로 보류한 항목에 사람이 답글로 결정을 적고 ▶️ 를 달면, 봇이
  그 답글을 새 지시로 집어 이어서 진행한다.
- **세부 규칙**:
  - 답글 지시는 부모 메시지 + 스레드 전문을 컨텍스트로 읽는다("그 항목"의 해석에 필요).
  - 스레드에 **미병합 PR 이 있으면 새 브랜치가 아니라 그 브랜치에 얹는다**(PR 갱신 —
    작업 파편화 방지). 이미 병합된 스레드의 새 답글은 새 브랜치.
  - 답글이 제품 결정을 담고 있으면 코드만 고치지 않고 **정책 파일이 지정한 결정 문서 반영
    커밋을 같은 PR 에 포함**한다 — 슬랙에만 남은 결정은 결정이 아니다(대상 레포 docs-first).
- **이유**: 이 루프가 없으면 티어 B(재량 필요)로 보류된 항목이 슬랙에 방치된다. 사람의 결정
  한 줄이 B 를 A 로 바꿔 자동 진행시키는 것이 이 시스템의 처리량을 결정한다.

## D-007 Q 티어 — 질문에는 결정을 요구하지 않고 답한다 (A·B 보완)

- **문제**: 3단계 첫 실사용에서 문의 성격의 4불릿이 전부 B 로
  분류됐다. 봇의 판정 근거는 정확했다 — "동작 설명을 요청하는 질문", "설명을 원하는 질문".
  규칙상 물음표로 끝나면 B 이기 때문이다. 그런데 **사람이 원한 것은 결정이 아니라 답변**이다.
  A(구현)도 B(결정 대기)도 아닌 것이 있는데 체계에 자리가 없어, 봇이 답할 수 있는 질문까지
  사람에게 되돌아갔다. 자동화의 목적(왕복 줄이기)이 정확히 반대로 작동한 셈이다.
- **결정**:
  - **① Q 티어 신설** — **바꾸라는 요구 없이 설명만 구하면 Q.** 봇이 코드·문서를 읽어 답글로
    답하고 ✅ 로 닫는다. 코드는 만들지 않는다(그건 A 다).
  - **② 제안이 섞이면 B 다.** "~하면 어때?"는 질문 형태여도 제품 결정을 요구한다. 이때는
    **답할 수 있는 부분은 답하고**(현행 동작·기존 결정) 남은 재량을 ❓ 로 남긴다 — 한 불릿이
    Q 와 B 를 겸할 수 있다.
  - **③ Q 의 답변에는 근거를 붙인다** — 파일 경로·문서·결정 번호. 근거 없이 답하면 그럴듯한
    추측이 사실로 스레드에 남고, 나중에 그걸 근거로 결정이 내려진다. **모르면 모른다고 적는다.**
  - **④ Q 답변은 결정을 내리지 않는다.** "이렇게 하는 게 좋겠어요"는 답변이 아니라 제안이고,
    제안은 B 다. Q 는 **있는 것을 설명하는 데까지**다.
  - **⑤ ✅ 의 의미를 넓힌다** — 종전에는 "병합 완료"였다. 이제 **"이 노드에서 할 일이 끝남"**
    이다(병합 완료 또는 답변 완료). 상태 기계의 종료 표시가 하나여야 사람이 훑기 쉽다.
- **이유**: 질문을 B 로 처리하면 사람은 "결정하라"는 요구를 받는데 정작 결정할 것이 없다.
  그 불일치가 쌓이면 ❓ 가 신호가 아니라 잡음이 되고, 진짜 결정이 필요한 항목이 묻힌다.
- **위험과 방어**: Q 는 봇이 **말을 만들어낼** 자리다(A 는 코드가, B 는 사람이 검증하지만 Q 는
  답변 자체가 산출물이다). 그래서 ③(근거 인용)과 ④(결정 금지)가 안전장치이고, 이 둘이 없으면
  Q 를 켜지 않는 편이 낫다.
- **연결**: D-001(정책이 경계를 정한다 — 프로젝트별 Q 범위는 `AUTOMATION.md`) · D-006.

## D-008 답하다 찾은 결함은 고친다 — 결함과 개선을 가르는 선 (D-007 보완)

- **문제**: Q 티어가 "설명까지"로 못 박히자, **답하다 발견한 명백한 결함까지 스레드에서
  죽었다.** 실사용에서 봇이 "두 경로가 같은 사실에 서로 다른 값을 낸다"를 찾아놓고
  "의도인지 결함인지 코드만으론 못 정한다"며 사람에게 넘겼다 — 그런데 결정 문서에 답이
  있었다. 판단할 근거를 손에 쥐고도 안 쓴 것이다.
- **결정**:
  - **① 정답이 문서·코드에 있으면 결함이고, 결함은 A 다.** 답하다 발견했더라도 그 자리에서
    A 로 올려 고친다. 예: 두 경로가 같은 사실에 다른 값을 낸다 · 결정 문서가 정한 규칙과
    코드가 어긋난다 · 확정된 문구가 어긋나 있다 · 죽은 코드·미사용 의존.
  - **② 정답이 없으면 개선이고, 개선은 B 다.** 예: 문구를 새로 짓는다 · 정보구조를 바꾼다 ·
    기능을 없애거나 더한다 · "이게 더 낫지 않나". 여기엔 재량이 있고 재량은 사람 몫이다.
  - **③ 가르는 질문은 하나**: *"무엇이 맞는지 문서·코드가 이미 말하고 있는가?"* 말하고 있으면
    고치고, 말하고 있지 않으면 판단 지점을 남긴다.
  - **④ 근거를 못 찾겠으면 찾아본 뒤에 넘긴다.** "코드만으론 모르겠다"로 끝내지 않는다 —
    결정 로그·설계 문서까지 보고도 답이 없을 때만 B 다. **어디를 찾아봤는지 답글에 적는다.**
  - **⑤ 고친 것은 답변과 함께 낸다.** 같은 스레드에 "이건 이렇게 동작합니다(설명) + 이건
    어긋나 있어 고쳤습니다(PR)"가 같이 간다.
- **바꾸지 않는 것**: D-007 ④(Q 답변이 제안을 하지 않는다)는 유지된다 — 제안과 결함은 다르다.
  안전·법무처럼 정책이 금지한 영역은 여전히 B(정책이 휴리스틱을 이긴다).
- **이유**: 자동화의 값은 "사람이 볼 것을 줄이는 것"인데, 답할 수 있는 것을 답하고 고칠 수
  있는 것을 안 고치면 목록만 길어진다. 반대로 재량까지 손대면 제품이 봇의 것이 된다.
  **정답의 유무**가 그 선이고, 그건 판정 가능한 기준이다.

## D-009 정책이 거는 것은 모델이 아니라 위임 대상(에이전트)

- **결정**: 정책 파일(`AUTOMATION.md`)의 `## 구현 규율` 은 구현 **모델 이름**이 아니라 그 레포
  `.claude/agents/` 의 **에이전트**와 **위임 금지 경로**를 지정한다. 엔진(`implement.md`)은
  그 지정을 읽어 A 항목의 구현 물량만 위임하고, 분류·판정·검증·PR 본문은 세션이 직접 한다.
- **왜 바꿨나**: 첫 소비자 정책에 "구현 모델: Sonnet 고정"이 반년 가까이 적혀 있었지만
  **한 번도 지켜지지 않았다.** 게을러서가 아니라 **엔진이 그 줄을 읽고 할 수 있는 일이
  없었기 때문**이다 — 세션은 자기 모델을 실행 중에 바꿀 수 없다. 실제 4단계 첫 PR 은
  상위 모델이 구현했고, 커밋 트레일러가 그 증거로 남았다.
- **일반화**: **실행할 수단이 없는 정책은 정책이 아니라 글이다.** 계약에 필드를 열 때는
  "엔진이 이걸 읽고 무슨 동작을 하는가"를 먼저 답할 수 있어야 한다. 답이 없으면 그 필드는
  지켜지지 않은 채 남아 다음 사람에게 **지켜지고 있다는 착각**을 준다.
- **예외를 함께 계약에 넣는다**: 값을 아끼면 안 되는 자리(안전·보안·되돌릴 수 없는 변경)는
  위임 금지 경로로 명시한다. 한 줄이라도 걸치면 그 항목 **전체**를 세션이 직접 구현한다.
  경로·주제로 구체적으로 적는다 — "중요한 곳"은 판정이 안 된다.
- **확인 장치**: 어느 쪽으로 구현했는지 답글과 PR 본문에 한 줄 남긴다. 없으면 지켜졌는지
  확인할 방법이 없고, 그러면 같은 일이 조용히 반복된다.

## D-010 사람 전용 이모지는 작성자까지 확인한다

- **결정**: ▶️·🚀 는 이름이 맞는 것으로 부족하다. **허용 목록에 있는 사용자가 붙인 것**만
  유효하다. 목록은 실행 인자(`--allow-users`)로 받고, 값은 환경변수로만 존재한다.
  목록이 비어 있으면 **아무것도 집지 않고 에러로 멈춘다.**
- **왜**: D-002 로 "봇은 자기를 트리거하지 못한다"를 코드로 막아 놓고, **남이 트리거하는
  문은 열어 둔 상태**였다. 검출은 `reactions` 의 이름만 봤고 슬랙이 함께 주는 `users` 를
  버렸다. 그래서 그 채널에 있는 누구든 ▶️ 하나로 봇에게 코드를 쓰게 하고, 🚀 하나로
  기본 브랜치에 병합시킬 수 있었다.
- **허용 목록 의미론**: 비어 있으면 **꺼진다**(전부 허용으로 뒤집지 않는다). 변수 하나를
  빠뜨린 것이 곧 문이 되면 안 된다. 그래서 `--allow-users` 는 **필수 인자**다 — 잊으면
  argparse 가 막는다.
- **스코프 비용 없음**: 판정에 필요한 `users` 는 `conversations.history` 응답에 이미
  실려 온다. 추가 스코프도 추가 호출도 필요 없었다.
- **남는 방벽**: 이 검사가 뚫려도 최악은 PR 한 건이다(기본 브랜치 직행은 없다). 그래도
  🚀 는 되돌리기 어려운 쪽이라 같은 규칙을 받는다.

## D-011 프로젝트 선언은 환경변수로, 루틴은 순회한다

- **결정**: 감시할 프로젝트 목록은 `AUTOPILOT_PROJECTS` 접미사 목록으로 선언한다. 루틴은
  `detect.py --all-projects` 로 전 프로젝트를 순회하고, 노드에 `project`·`repo`·`channel`
  이 실린다. 프로젝트를 추가할 때 **트리거를 새로 만들지 않는다.**
- **왜**: `engine.md` 는 처음부터 "루틴 하나가 채널↔레포 매핑을 순회한다"고 적어놨고
  `config.json` 에 그 자리도 있었다. 그런데 **그 파일을 읽는 코드가 하나도 없었다.**
  실제로는 트리거 프롬프트에 `$SLACK_CHANNEL_ID_SAI` 같은 프로젝트별 이름이 박혀 있어서,
  프로젝트를 하나 붙일 때마다 트리거 4개(구현 3 + 병합 1)를 새로 만들어야 했다.
- **설정 파일을 지운 이유**: 파일이 존재한다는 사실이 **"순회가 구현돼 있다"는 착각**을
  만들었다. 읽히지 않는 설정은 설정이 아니라 장식이고, 장식은 다음 사람을 속인다.
  D-009 와 같은 종류의 실수다 — **실행할 수단이 없는 선언**.
- **왜 파일이 아니라 환경변수인가**: 엔진 레포에 프로젝트 이름을 둘 수 없다(D-001 ④).
  파일로 두면 그 파일이 곧 프로젝트 목록이 되어 범용성이 깨진다.
- **접미사 규약을 고른 이유**: 이미 `SLACK_CHANNEL_ID_SAI` 처럼 접미사로 쓰고 있었다.
  새 DSL 을 만드는 대신 있는 관례를 형식화했다.
- **허용 사용자는 프로젝트별로 다를 수 있다**: 채널이 다르면 주인이 다르다.
  `SLACK_HUMAN_USERS_{S}` 가 있으면 그것을, 없으면 전역을 쓴다. 어느 쪽도 비어 있으면
  터진다(D-010 — 빠뜨렸을 때 꺼지는 쪽).

## D-012 "검사가 없음"은 정책이 판정한다

- **결정**: CI 상태가 `none`(붙은 검사 0건)일 때, 정책의 `## 검증` 이 선언한 "검사가 안
  붙는 것이 정상인 경로" 안에 **바뀐 파일이 전부** 들어가면 병합한다. 선언이 없거나 목록
  밖 파일이 하나라도 섞이면 ❓ 로 묻는다. 선언하지 않았을 때의 기본은 **묻는다**.
- **왜**: `none` 을 무조건 사람에게 묻게 했더니, **문서만 고친 PR 이 닷새간 다섯 번**
  같은 질문을 반복했다. sai 의 CI 는 `paths:` 필터라 `docs/**` 만 바뀐 PR 에는 검사가
  애초에 안 붙는다 — 결함이 아니라 설계다. 그런데 엔진은 그것을 "읽지 못한 상태"와
  똑같이 취급했다.
- **가르는 선**: **못 읽은 것(사고)과 원래 없는 것(설계)은 다르다.** `unreadable` 은
  여전히 무조건 사람에게 간다. `none` 만 정책 판정 대상이다.
- **한 파일이라도 밖이면 예외가 깨진다**: 문서 PR 에 코드를 끼워 넣어 검사를 통째로
  건너뛰는 경로를 막는다. 판정은 `pr-files` 로 실제 파일 목록을 봐서 한다.
- **함께 고친 것 — 사람이 접을 문**: 병합 모드가 ✅ 만 종료로 봐서, 사람이 ❌ 를 붙여도
  매 실행 다시 잡혔다. 🚀 를 떼는 것이 유일한 출구였고 아무도 그걸 모른다. ❌ 를 두 모드
  모두에서 종료로 본다 — **사람에게는 언제나 나가는 문이 있어야 한다.**

## D-013 주기는 1시간이 기본 — 유휴 실행이 곧 비용이다

- **결정**: 클라우드 루틴의 주기는 플랫폼 최소 간격인 **1시간을 그대로 쓴다.** 오프셋
  트리거로 촘촘하게 만드는 것은 **그럴 이유가 실측으로 있을 때만** 한다.
  현재: 구현 매시 `:00` · 병합 매시 `:30` (트리거 2개).
- **왜 되돌리나**: 20분 주기(오프셋 3개)로 깔았더니 **하루 76회 · 월 2,280회**가 됐는데,
  그중 실제로 일한 실행은 열흘 동안 한 자릿수였다. **99% 이상이 "할 일 없음"** 이다.
- **유휴가 싸다는 말의 오해**: 유휴 경로는 "클론 → detect → 종료"라 **출력**은 거의 없다.
  그러나 매 실행이 **세션 하나를 띄운다** — 시스템 프롬프트·도구 정의·커넥터 스키마가
  통째로 입력에 실린다. 부트스트랩 프롬프트는 1,654자로 그 옆에서 반올림 오차다.
  **줄여야 할 것은 프롬프트가 아니라 실행 횟수였다.**
- **함께 줄인 것**: MCP 커넥터를 넷에서 둘로(PlayMCP·Notion 제거 — 이 엔진은 슬랙을
  python 으로 직접 부르므로 쓸 일이 없었다). 커넥터 스키마도 매 실행 입력이다.
- **반응 지연의 값**: ▶️ 를 달고 최대 1시간을 기다린다. 사람이 이모지를 다는 빈도가
  하루 한두 번이라 이 지연은 실사용에서 문제가 되지 않는다. 급하면 수동 실행이 있다.
- **건드리지 않은 것**: `allowed_tools` 축소는 이득이 있어 보이지만 한 번 크게 데었다 —
  `["Bash"]` 로 묶었더니 MCP 커넥터가 빠지며 GitHub 프록시 경로까지 닫혔다. 위험 대비
  이득이 불확실해 따로 재보기 전에는 손대지 않는다.
