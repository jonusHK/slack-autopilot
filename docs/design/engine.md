# 설계 — 엔진 (상태 기계 · 파이프라인 · 락)

- 상태: 초안 (2026-08-13) — sai `docs/runbook/slack-automation.md` §1·2·4·5·6·7 을 엔진
  명세로 이관한 것. 결정의 근거는 `../decisions.md`(D-001~006).
- 이 문서에 **프로젝트 이름이 나오면 안 된다**(D-001 ④). 프로젝트별 값은 전부
  `policy-contract.md` 의 정책 파일 몫이다.

## 1. 상태 기계 — 이모지가 유일한 제어 표면

| 이모지 | 의미 | 붙이는 주체 | 다음 |
|---|---|---|---|
| ▶️ | 진행 필요 | **사람만** | 루틴이 집는다 |
| 💬 | 처리 중(클레임) | 루틴 | 구현 진행 |
| 🧵 | PR 생성됨 — 스레드에 링크·작업내역 | 루틴 | 사람 검토 대기 |
| ❓ | 결정 필요 — 판단 지점을 답글로 | 루틴 | 사람이 답글로 결정(→§2) |
| 🚀 | 병합 진행 | **사람만** | 병합 루틴이 순차 처리 |
| ✅ | 기본 브랜치 병합 완료 — 충돌 해소 기록 답글 | 루틴 | 종료 |
| ❌ | 실패 — 원인·로그 링크 답글 | 루틴 | 사람 판단 |

- **봇은 ▶️·🚀 를 절대 붙이지 않는다**(D-002) — 자기 트리거 금지가 무한 루프를 막는다.
- 이모지는 사람이 보는 표시다. **기계의 락은 원격 브랜치**(§3).

## 2. 작업 노드 — ▶️ 달린 메시지 **또는 스레드 답글**

검출 대상: **최근 7일 · ▶️ 있고 💬 없음.** 부모 메시지와 스레드 답글을 구분하지 않는다(D-006).

```
봇: ❓ + "판단 지점 A/B" 답글
사람: (답글) "A 로. 문구는 이걸로." + 그 답글에 ▶️
봇: 답글을 새 지시로 집어 이어서 진행
```

- 답글 지시는 **부모 메시지 + 스레드 전문**을 컨텍스트로 읽는다.
- 답글에 담긴 제품 결정은 코드만 고치지 않는다 — **정책 파일이 지정한 결정 문서의 반영
  커밋을 같은 PR 에** 포함한다.

## 3. 락과 멱등성

- **클레임 = 원격 브랜치 push**: `auto/slack-{message_ts}`. push 가 원자적이라 이모지 반영이
  늦어도 두 루틴이 같은 노드를 두 번 집지 못한다. 순서는 **브랜치 push → 💬**.
- **브랜치 재사용**: 스레드에 미병합 PR 이 있으면 그 브랜치에 얹는다(PR 갱신). 병합된
  스레드의 새 답글은 새 브랜치(`auto/slack-{reply_ts}`).
- **상태를 기억에 두지 않는다**(D-003 ④): 모든 전이가 "이모지 유무 + 브랜치 유무"로
  판정된다. 루틴이 중간에 죽어도 다음 실행이 같은 지점에서 이어간다.
- 유휴 시 즉시 종료 — ▶️ 없으면 토큰 소비 0 에 가깝게. 매시 실행의 대부분이 이 경로다.

## 4. 파이프라인

```
[매시] 검출(▶️ 있고 💬 없는 노드, 채널↔레포 매핑 순회)
  → 대상 레포 클론 → AUTOMATION.md 읽기 (없으면 전 항목 ❓ — D-001 ③)
  → 클레임: 브랜치 push + 💬
  → 노드당 에이전트 1개 (워크트리 격리 · 동시 상한 · 정책이 지정한 구현 모델)
  → 불릿 단위 티어 분류(정책 기준) → A 만 구현, B 는 보류 목록
  → push → PR 생성 → CI → 자기 수정 루프(§5)로 그린
  → 스레드에 PR 링크 + 작업내역 + "처리 N건 / 보류 M건(사유별)" + 🧵
[사람] PR 검토 → 🚀
[병합 루틴] 🚀 있고 ✅ 없는 것만 순차 병합 → ✅ (충돌 해소 기록 답글)
```

- **티어 분류는 메시지가 아니라 불릿 단위**다. 한 메시지에 성격이 다른 항목이 섞인다.
  범용 휴리스틱: *무엇을 할지가 정해져 있고 어떻게만 남았으면 A, 무엇에 재량이 있으면 B.
  물음표로 끝나는 불릿·"검토"·"~어때"는 무조건 B.* 세부 경계는 정책 파일이 정한다.
- **처리/보류 집계를 항상 답글에** — 조용히 빠진 항목이 없어야 한다.
- **e2e·무거운 검증을 에이전트가 직접 돌지 않는다** — 대상 레포 CI 가 한다(D-003 ②).
- 동시 상한(기본 3)은 자원이 아니라 **병합 충돌 표면**을 줄이는 값이다.

## 5. 자기 수정 루프 (D-004)

```
push → CI 실패 → gh run view --log-failed → 원인 수정 → push → (반복)
```

- 상한 **5회 / 60분**. 초과 시 ❌ + 마지막 실패 요약 답글 후 정지.
- 그린으로 인정하지 않는 것: **가드 우회**(`SKIP_*` 류) · **테스트 약화**(단언 삭제·skip).
  이 경우는 즉시 ❌.

## 6. 병합 루틴 (D-005)

- 자동 병합 없음 — 🚀 (사람) 이후에만, **순차**로.
- 병합 직전 **재번호**: 순번 파일(마이그레이션·결정 로그 등 — 정책 파일이 규칙을 지정)의
  번호 충돌은 규칙 기반이라 자동 해소한다. 아직 기본 브랜치에 없는 새 파일이라 안전하다.
- **금지선(❓ 로 사람에게)**: 로직 충돌(같은 함수 본문 양쪽 변경) · 정책 지정 금지선 파일
  충돌 · 정책 지정 민감 경로 변경 포함 PR.
- 완료 시 ✅ + 충돌을 어떻게 해소했는지 답글 기록.

## 7. 실행 표면 (D-003)

- **클라우드 루틴**(cron, 매시 — 정각 회피 분 선택). 루틴 하나가 채널↔레포 매핑을 순회한다.
  클레임이 노드 단위라 프로젝트 수가 늘어도 안전하다.
- **슬랙 접근은 봇 토큰 + Web API**: `conversations.history` · `conversations.replies` ·
  `reactions.get` · `reactions.add` · `chat.postMessage`. 커넥터(MCP) 의존 금지.
- GitHub 접근은 클라우드 에이전트의 GitHub 연동 + `gh`.
- 토큰·자격은 시크릿으로만(값을 코드·문서·로그에 남기지 않는다).

## 8. 엔진 설정

```yaml
# config.yaml (예시 — 시크릿 아님. 토큰은 환경변수)

  - channel: "<채널 ID>"
    repo: "<owner>/<repo>"       # AUTOMATION.md 가 있어야 처리한다

detect_window_days: 7
```

## 9. 이 문서가 정하지 않는 것

1. 티어 A/B 의 프로젝트별 경계 — 정책 파일(`policy-contract.md`).
2. 이모지 최종 확정 — 1일 실사용 후 조정(누르기 편한지).
3. 실패 알림 채널 — ❌ 를 답글 외 푸시로도 보낼지.
4. 루틴 프롬프트·스크립트의 구체 구현 — 착수 순서(`../runbook/setup.md`)대로 단계 도입.
