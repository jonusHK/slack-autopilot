# 트러블슈팅

증상 하나에 항목 하나. **증상 → 진짜 원인 → 조치** 만 남기고 디버깅 과정은 버린다.
넣는 기준은 걸린 시간이 아니라 **재발 가능성과 오해 유발성**이다. **음성 결과**
("조사해봤더니 원인이 아니었다")도 같은 값어치로 남긴다 — 다음 사람이 그 길을 또 판다.

실행 환경의 일반적 차이는 [design/runtime.md](design/runtime.md) §2.5, 규칙은
[design/engine.md](design/engine.md).

## 루틴이 GitHub 에 접근하지 못한다 (403 · could not read Username)

- 마지막 확인: 2026-08-16(실측)

### 증상

클라우드 루틴에서 대상 레포를 건드리는 것이 전부 실패한다. 증상은 단계마다 다르게 보인다.

```
fatal: could not read Username for 'https://github.com': terminal prompts disabled
GitHub access is not enabled for this session. (HTTP 403)
An org admin must connect the Claude GitHub App for this organization.
```

로컬에서는 같은 스크립트가 멀쩡히 돈다.

### 진짜 원인 — 둘 다 루틴 설정이었다

**① 루틴에 레포지토리가 안 붙어 있었다.**

루틴은 "프롬프트 + **레포지토리** + 커넥터"로 이루어진다. 웹 폼으로 만들면 레포 선택이
필수 단계라 빠뜨릴 수 없지만, **HTTP API 로 만들면 그 항목 없이도 생성된다.** 그러면
세션의 GitHub 프록시가 "이 세션에 등록되지 않은 레포"로 보고 **git 도 API 도** 막는다.

API 필드 이름은 `job_config.ccr.session_context.sources` 다.

```json
"sources": [{"git_repository": {"url": "https://github.com/OWNER/REPO"}}]
```

**이름을 틀리면 조용히 버려진다.** `repos`·`repositories` 로 보내면 200 이 오고 응답에서
그 필드만 사라진다. 검증 오류가 아니다 — **응답을 다시 읽어 실제로 실렸는지 확인해야 한다.**

**② `allowed_tools` 를 좁게 잡으면 GitHub 경로가 함께 닫힌다.**

최소 권한이라 생각하고 `["Bash"]` 로 묶었는데, 그러면 MCP 커넥터 도구가 통째로 빠지고
프록시가 자격을 붙이는 경로까지 닫힌다. 레포를 붙인 뒤에도 **git 은 되는데 REST API 만
403** 인 상태가 이것이다. 제한을 풀자 같은 세션에서 API 가 200 으로 바뀌었다.

### 조치

루틴을 API 로 만들 때 **`sources` 를 반드시 넣고, `allowed_tools` 로 조이지 않는다.**
넣은 뒤에는 응답의 `session_context` 를 다시 읽어 두 값이 살아 있는지 확인한다.

레포가 붙었는지는 세션 안에서도 확인할 수 있다.

```
mcp__Claude_Code_Remote__add_repo(owner=…, repo=…, access="push")
→ {"status":"already_present", ...}   # 이미 붙어 있음
```

### 원인이 아니었던 것 넷 (음성 결과)

여기서 시간을 가장 많이 태웠다. 전부 실측으로 배제했다.

| 의심 | 배제 근거 |
|---|---|
| 토큰 권한·형식이 잘못됐다 | `GET /user` 가 **200** 으로 계정명을 돌려줬다. 토큰은 처음부터 정상 |
| 토큰이 아예 필요하다 | **절반만.** 레포를 붙이면 클론·push·PR 조회는 토큰 없이 통한다(프록시가 붙인다). 하지만 **CI 상태 조회는 403** 이다 — 그건 토큰이 필요하다. "토큰 없이 전부 된다"고 판정했다가 되돌렸다: 프로브 요약 한 줄만 읽고 항목별 결과를 안 봤다 |
| Claude GitHub App 이 안 깔렸다 | 이미 설치돼 있었고 대상 레포도 목록에 있었다(읽기·쓰기 전권) |
| `/web-setup` 을 안 했다 | 하고 나서도 API 403 은 그대로였다. `/web-setup` 은 **클론까지만** 열어준다 |
| 브랜치 접두사가 `claude/` 여야 한다 | `auto/` 도 dry-run push 가 통과했다. 문서의 "`claude/` 는 항상 허용"은 **다른 이름이 막힌다는 뜻이 아니다** |

### 진단이 헛돈 이유

**403 을 코드로만 보고 본문을 안 봤다.** 본문에는 처음부터 답이 적혀 있었다.

```
"GitHub access to this repository is not enabled for this session.
 Use add_repo to request access."
```

이 한 줄을 일찍 읽었으면 토큰·App·계정 연결을 뒤질 이유가 없었다. **자격 문제로 보이는
403 일수록 응답 본문을 먼저 읽는다.**

또 하나 — **인증 없이 퍼블릭 엔드포인트를 부르는 대조군**이 결정적이었다. 그것마저 403 이면
GitHub 이 거부하는 게 아니라 **중간에 프록시가 있다**는 뜻이다. 자격을 의심하기 전에 이걸 먼저 잰다.

## 실패 알림이 채널에 반복해서 쌓인다

- 마지막 확인: 2026-08-15(실측)

### 증상

같은 실패 메시지가 20분마다 채널에 쌓인다.

### 진짜 원인

실패 조건이 지속되는 동안 매 실행이 독립적으로 실패를 보고한다. 루틴은 무상태라
**직전 실행이 이미 같은 말을 했는지 모른다.**

### 조치

원인을 고치는 동안에는 **트리거를 꺼둔다.** 알림 자체를 없애는 것보다 낫다 — 침묵은
"고쳐졌다"로 오해되지만, 꺼둔 트리거는 목록에서 보인다.

항구적으로는 보고 전에 채널 최근 메시지를 읽어 같은 실패가 이미 있으면 건너뛴다.

## 진단용 실행 결과를 낡은 메시지로 착각한다

- 마지막 확인: 2026-08-16(실측)

### 증상

프로브를 다시 돌리고 결과를 읽었는데 **바뀐 게 없다.** 실제로는 이전 실행의 메시지를
읽고 있었다.

### 진짜 원인

채널 최근 메시지를 "제목이 같은 것"으로 찾으면 **직전 실행의 결과가 먼저 잡힌다.**
"최근 15분 이내" 같은 창으로 걸러도, 실행 간격이 그보다 짧으면 소용없다.

### 조치

**실행을 시작한 시각을 기준선으로 잡고 그보다 새 메시지만** 읽는다. 제목이나 시간 창으로
거르지 않는다. 이걸로 한 라운드를 통째로 날렸고, 그 사이 "여전히 안 된다"는 잘못된
보고를 했다.

## 로그를 잘라 받고 "없다"고 결론 낸다

- 마지막 확인: 2026-08-16(실측)

### 증상

두 환경을 비교해 "이쪽에는 그 에러가 0건"이라고 판단했는데 사실이 아니다.

### 진짜 원인

출력을 `tail -60` 으로 받아놓고 전체를 본 것처럼 셌다. 그 에러는 앞부분에 64번 있었다.

### 조치

**개수를 세려면 전체를 파일로 받는다.** 잘라 본 출력에서 나온 "0건"은 근거가 아니다.
비교 판단의 근거로 쓸 값이라면 특히 그렇다.
