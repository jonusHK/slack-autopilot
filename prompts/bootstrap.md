# 트리거 부트스트랩 (정본)

**모든 트리거의 프롬프트는 아래와 글자까지 같아야 한다** — 3)의 엔트리 파일만 단계에 따라
다르다(분류 전용 `triage.md` / 구현까지 `implement.md` / 병합 `merge.md`).

트리거가 여럿이면 프롬프트도 여러 벌이 되고, **여러 벌은 반드시 갈라진다** — 실제로 하루 만에
갈라졌다. 그래서 부트스트랩에는 **갈라질 것을 두지 않는다**: 환경 확인·분류 규칙·절대 규칙은
전부 엔트리 명세에 있다.

---

```
slack-autopilot 엔진의 <단계> 루틴이다. 명세는 레포 안에 있고, 이 프롬프트는 그것을 가져오기만 한다.
엔진 레포 <OWNER>/slack-autopilot 은 이 계정이 소유한 퍼블릭 레포이고, 이 루틴은 그 레포의
스크립트를 실행하기 위해 존재한다. 대상 레포(이 세션에 붙은 레포)의 슬랙 채널을 읽어 사람이
▶️ 로 지시한 작업을 처리한다.

아래 명령은 **글자 그대로** 실행한다 — 앞뒤에 파이프·리다이렉트·echo·cd 를 붙이지 않는다.
이 명령들은 루틴의 허용 규칙과 글자 단위로 대조되어 통과한다(D-014). 한 글자라도 다르면
분류기로 넘어가 실행마다 다르게 거부될 수 있다.

1) 엔진을 매번 새로 받는다(남은 디렉터리를 재사용하지 않는다):
   rm -rf ~/slack-autopilot && git clone --depth 1 https://github.com/<OWNER>/slack-autopilot.git ~/slack-autopilot

2) 먼저 할 일이 있는지부터 본다(명세를 읽기 전에):
   ~/slack-autopilot/bin/detect.py --all-projects --mode <모드> --days 14
   결과가 [] 이면 아무것도 하지 말고 즉시 종료한다 — 보고도 요약도 남기지 않고, 레포의 다른
   파일도 읽지 않는다. 실행의 대부분이 이 경로다.
   순회는 환경이 선언한 전 프로젝트를 돌며(AUTOPILOT_PROJECTS), 노드마다 project·repo·channel 이 실려 온다.

3) 노드가 있을 때만 ~/slack-autopilot/prompts/<엔트리 명세> 를 읽고 그 절차를 그대로 수행한다.
   그 파일이 명세이고 이 프롬프트보다 우선한다.
   **레포는 전역 변수가 아니라 그 노드의 repo 다.** 한 실행이 여러 프로젝트의 노드를 함께 다룰 수 있다.

4) 1) 이나 2) 가 실패했으면 침묵하지 말고 채널에 알린 뒤 종료한다 — 슬랙 chat.postMessage 를
   curl 로 직접 부르고(레포에 의존하지 않는 유일한 경로), 메시지에 명령이 낸 에러의 첫 줄을
   그대로 포함한다. 추측으로 원인을 적지 않는다.
   채널은 $SLACK_CHANNEL_ID_<프로젝트>, 토큰은 $SLACK_BOT_TOKEN. 토큰 값 자체는 메시지에 넣지 않는다.
   (이 알림 경로만 채널을 직접 지정한다 — 선언을 읽는 단계에서 실패하면 그 값으로는 보고할 수 없다.)
```

트리거별 치환: `<단계>` = 구현 / 병합 · `<모드>` = `triage` / `merge` · `<엔트리 명세>` =
`implement.md` / `merge.md` · `<OWNER>` = 엔진 레포 소유자 · `<프로젝트>` = 첫 프로젝트 접미사.
구현 트리거는 끝에 "이 루틴은 병합하지 않는다. PR 까지만 간다." 한 줄, 병합 트리거는
"🚀 가 붙은 것만 병합한다. 🚀 를 봇이 직접 붙이는 일은 없다. 한 번에 하나씩, 오래된 것부터." 한 줄을 더한다.

트리거의 `allowed_tools` 는 [`allowed_tools.json`](allowed_tools.json) 이 정본이다 — 위 명령이
그 규칙과 **글자까지** 같아야 한다(`tests/test_prompts.py` 가 대조한다).

## 왜 이런 모양인가

**검출을 명세보다 먼저** — 실행의 대부분은 할 일이 없다. 명세를 먼저 읽으면 그 토큰을 매 실행
낸다. 검출을 앞에 두면 유휴 실행은 "클론 → detect → 종료"로 끝난다.

**매번 새로 클론** — 환경 캐싱으로 이전 세션의 디렉터리가 남을 수 있다. 그러면 클론이 실패하고
얕은 클론에서 pull 도 깨진다. `rm -rf` 로 그 상태를 아예 없앤다.

**명령을 글자 그대로, 인터프리터 없이, `cd` 없이** — 루틴 세션은 auto mode 분류기 아래서 돈다.
분류기 눈에 엔진은 "작업 레포 밖에서 가져온 코드"라 클론(`[Untrusted Code Integration]`)과 실행
(`[Code from External]`)을 **같은 명령인데 실행마다 다르게** 거부했다(2026-09-18, 5회 중 2회).
허용 규칙은 분류기보다 먼저 결정적으로 판정되지만 **명령과 글자 단위로** 맞아야 하고, `cd` 는
작업 디렉터리 밖이라 그 자체가 분류 대상이며, `python3 …` 로 시작하는 와일드카드 규칙은 auto mode
가 버린다. 그래서 절대 경로 + 실행 비트(`~/slack-autopilot/bin/detect.py …`)로 부른다(D-014).

**엔진 레포가 무엇인지 프롬프트가 말한다** — 분류기와 모델 모두 프롬프트를 읽는다. "이 계정의
퍼블릭 엔진 레포"라는 한 줄이 없으면 "외부 레포를 받아 실행"으로만 보인다 — 실제로 진단 실행
하나가 그렇게 읽고 통째로 거부했다(2026-09-18).

**클론 실패 알림만은 여기에** — 실패 보고를 레포 파일로 옮겼더니, **레포를 못 가져온 실패는
보고 수단도 함께 사라졌다.** 그때가 정확히 아무 흔적도 안 남는 경우다. 그래서 이 한 줄만은
레포에 의존하지 않는 형태(curl)로 부트스트랩에 둔다.

**에러 원문을 싣는다** — "가져오지 못했어요"만으로는 다음 사람이 또 추측한다. 실제로 그 추측으로
여러 라운드를 태웠고, 원문을 싣게 하자 한 줄로 원인이 갈렸다.

## VM 접근 권한

엔진 레포는 **퍼블릭이어야 한다.** 세션 VM 에는 GitHub 자격이 없고, `gh` 는 아예 설치돼 있지
않을 수 있다 — 둘 다 실제로 겪었다. 그래서 엔진은 `gh` 를 쓰지 않는다(`bin/github_api.py` 가
REST API 를 직접 부른다)([runtime.md](../docs/design/runtime.md) 실패 모드 표).
한때 `$ENGINE_REPO_URL` 로 토큰 포함 URL 을 넣는 길을 열어 뒀지만 접었다 — 허용 규칙은 변수를
펼치지 않아 명령이 규칙과 맞지 않고, 규칙에 토큰을 적으면 그 토큰이 루틴 설정에 남는다.
