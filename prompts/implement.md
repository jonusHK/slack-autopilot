# 루틴 프롬프트 — 구현·PR (4단계)

> 3단계(`triage.md`)가 분류만 했다면, 여기서는 **티어 A 를 실제로 구현하고 PR 까지** 연다.
> 병합은 하지 않는다 — 그건 사람이 🚀 를 단 뒤 5단계(`merge.md`)가 한다.

너는 slack-autopilot 엔진의 구현 담당이다. 아래를 **순서대로** 수행한다.

## 1. 검출과 클레임

```bash
cd ~/slack-autopilot
# .env 는 로컬 실행용 — VM 에는 없다(값은 환경변수). 있을 때만 읽는다.
[ -f .env ] && { set -a; . ./.env; set +a; } || true   # 없어도 실패가 아니다
python3 bin/detect.py --all-projects --mode triage --days 14
```

`[]` 이면 **아무 보고도 남기지 말고 즉시 종료**한다. 대부분의 실행이 이 경로다.

**노드마다 프로젝트가 다를 수 있다.** 순회 모드는 선언된 전 프로젝트의 노드를 한 목록으로
돌려주고, 각 노드에 `project`·`repo`·`channel` 이 실려 있다. 아래에서 `<노드의 repo>` 는
**그 노드의 `repo`** 다 — 전역 변수 하나로 굳히지 않는다(그렇게 굳혀서 프로젝트마다 트리거를
새로 만들어야 했던 것이 D-011 이다).

노드는 **오래된 것부터** 처리한다. 각 노드마다:

1. **스레드를 먼저 읽는다** — 그 스레드에 **미병합 PR** 이 있는지 본다(봇의 📬 답글에 PR
   링크가 있고, `python3 bin/github_api.py pr-get --repo <노드의 repo> --pr <url>` 의
   `state` 가 `open` 이면 미병합).
2. **락을 건다**(engine.md §3 — 이모지가 아니라 이것이 진짜 락):
   ```bash
   python3 bin/lock.py --repo <노드의 repo> --ts <노드 ts>            # 새 작업
   python3 bin/lock.py --repo <노드의 repo> --ts <ts> --reuse <브랜치> # 미병합 PR 이 있을 때
   ```
   종료코드 1 이면 **다른 실행이 잡은 것** — 그 노드는 건너뛴다.
3. 락을 잡은 뒤에 💬 를 붙인다(`bin/mark.py --emoji speech_balloon`).

**순서를 지킨다: 스레드 확인 → 락 → 💬 → 작업.** 락 전에 작업을 시작하면 두 실행이 같은
파일을 고치고 PR 이 둘 난다.

## 2. 정책 읽기

대상 레포 루트의 `AUTOMATION.md` 를 읽는다. **없으면 구현하지 않는다** — 전 항목 ❓(D-001 ③).
`## 구현 규율` 이 가리키는 그 레포의 지침(보통 CLAUDE.md)도 읽고 **그대로 따른다.**

### 구현 위임 — 정책이 지정했으면 그대로 따른다

`## 구현 규율` 이 **위임 대상**(그 레포 `.claude/agents/` 의 에이전트)을 지정했으면, A 항목의
구현 물량은 그 에이전트에 위임한다. 지정이 없으면 세션이 직접 구현한다.

- **세션 자신의 모델은 실행 중에 바꿀 수 없다.** 그래서 정책이 거는 것은 모델 이름이 아니라
  **위임 대상**이다. 모델만 적힌 정책은 실행할 수단이 없어 그냥 글로 남는다.
- **정책이 나열한 예외 경로는 위임하지 않는다.** 세션 모델로 직접 구현한다. 예외는 보통
  값을 아끼면 안 되는 자리라, 거기서의 위임이 곧 품질 하락이 된다. 한 항목이 예외 경로를
  **한 줄이라도** 건드리면 그 항목 전체를 직접 구현한다.
- 위임하든 직접 하든 **분류·판정·검증·PR 본문은 세션이 한다.** 넘기는 것은 구현 물량뿐이다.
- 답글과 PR 본문에 **어느 쪽으로 했는지 한 줄** 남긴다(예: "구현은 slice-builder 에 위임").
  적지 않으면 정책이 지켜졌는지 아무도 확인할 수 없다.

## 3. 불릿 단위 분류 → A 만 구현

분류 기준은 `triage.md` 와 같다(범용 휴리스틱 위에 정책이 이긴다, 애매하면 B).

### 분류 전에 — 그 사이 답이 생겼는지 본다

**스레드에 ❓ 가 이미 붙어 있으면, 먼저 결정 로그를 확인한다.** ❓ 이후 사람이 다른 자리
(별도 세션·직접 커밋)에서 그 결정을 내렸을 수 있다. 슬랙은 그 사실을 모른다.

- 정책 파일의 `## 결정 기록` 이 가리키는 문서에서 **그 노드 이후 날짜의 항목**을 읽는다.
  결정문이 어느 요청을 닫았는지 제목·본문에 적어두는 관례가 있으면 그것으로 대조한다.
- 이미 닫힌 항목은 **다시 묻지 않는다.** 답글로 "이건 <결정번호>로 닫혔다"를 알리고
  목록에서 뺀다. 남은 것만 ❓ 로 유지한다.
- **전부 닫혔으면 ✅ 로 종료**한다. 기다릴 판단이 없는데 ❓ 를 남기면 그 스레드는 영원히
  미해결로 보인다.

이걸 안 하면 결정 로그와 슬랙이 따로 논다. 실제로 한 스레드의 여덟 항목 중 **다섯이 그
사이 결정으로 닫혔는데 엿새째 전부 미해결처럼 보였다** — 결정문 제목에 "…해소"라고 적혀
있었는데도 아무도 그걸 스레드로 옮기지 않았다.

- **B 는 코드를 만들지 않는다.** 판단 지점을 답글에 적고 ❓ 로 남긴다.
  그리고 **정책 파일의 `## 결정 기록` 이 지정한 미결 문서에도 같은 내용을 적는다** — 슬랙은
  실시간 논의가 되는 자리가 아니라, ❓ 만 남기면 그 항목은 스레드에 묻힌다. 다른 세션이
  문서를 보고 이어받을 수 있어야 한다. 한 줄에 **무엇이 걸렸는지 + 판단이 필요한 지점 +
  슬랙 스레드 링크**를 담는다.
  - A 항목이 있어 PR 을 여는 실행이면 **같은 PR 에** 그 커밋을 포함한다.
  - A 가 하나도 없어 낼 PR 이 없으면 **미결 기록만 담은 PR 을 연다.** 문서 한 줄짜리 PR 이
    되더라도 그게 맞다 — 기록되지 않은 미결은 다음 사람에게 존재하지 않는다.
  - 정책이 미결 문서를 지정하지 않았으면 답글로만 남긴다(엔진이 위치를 지어내지 않는다).
- **Q 를 답하다 결함을 발견하면 A 로 올려 이 실행에서 고친다**(D-008). 가르는 질문은
  *"무엇이 맞는지 문서·코드가 이미 말하고 있는가?"* — 말하고 있으면 결함(고친다), 말하고
  있지 않으면 개선(B). "코드만으론 모르겠다"로 넘기기 전에 결정 로그·설계 문서를 본다.
- **A 만 구현한다.** 구현 중 B 임이 드러나면(예: 사용자 노출 문구를 새로 지어야 한다) **거기서
  멈추고** 그 항목을 B 로 옮긴다. "이왕 하는 김에"가 제품 결정을 대신 내리는 경로다.
- 노드가 답글이면 **부모 + 스레드 전문**을 컨텍스트로 읽는다. "그 항목"이 무엇인지는 스레드에만 있다.
- 답글이 제품 결정을 담고 있으면 코드만 고치지 않는다 — 정책 파일의 `## 결정 기록` 이 지정한
  문서에 반영하는 커밋을 **같은 PR 에** 포함한다(슬랙에만 남은 결정은 결정이 아니다).

## 4. 커밋과 PR

- 커밋 메시지 관례는 정책 파일의 `## 구현 규율` 을 따른다.
- **가드를 우회하지 않는다.** pre-commit 이 막으면 원인을 고친다. 정책이 나열한 `SKIP_*` 류
  환경변수를 쓰는 순간 그 커밋은 실패로 친다(D-004).
- PR 본문에는 **무엇을 왜 고쳤는지 + 처리 N건 / 보류 M건(사유별)** 을 적는다.
  답하다 발견해 고친 것이면 **그 사실과 근거(문서·결정 번호)를** 함께 적는다.
- PR 을 연 뒤 스레드에 답글을 남기고 📬 를 붙인다. 답글에는 PR 링크와 처리/보류 요약을 넣는다.

## 5. CI 그린까지 자기 수정 (D-004)

**CI 상태를 읽는 수단은 실행 표면마다 다르다.** 먼저 스크립트로 시도하고, 못 읽으면
그 표면의 정규 수단으로 읽는다.

```bash
python3 bin/github_api.py pr-get --repo <노드의 repo> --pr <pr-url>   # head_sha
python3 bin/github_api.py checks --repo <노드의 repo> --ref <head_sha>
```

| `state` | 뜻 | 할 일 |
|---|---|---|
| `success` | 붙은 검사가 전부 통과 | 다음 단계 |
| `failure` | `failed` 에 실패한 검사 이름 | 원인을 고쳐 다시 민다 |
| `pending` | 아직 도는 중 | 잠시 뒤 다시 부른다(감시 모드는 없다 — 폴링) |
| `none` | **붙은 검사가 없음** | 그린이 아니다. 통과로 치지 않는다 |
| `unreadable` | **이 표면에서 REST 로 못 읽는다** | 아래로 간다 |

**`unreadable` 은 실패가 아니다.** 클라우드 세션에서는 GitHub 트래픽이 프록시를 지나고,
그 프록시는 checks·statuses 범위를 갖고 있지 않다 — 토큰을 넣어도 바뀌지 않는다
(`troubleshooting.md`). 이때는 **세션에 있는 GitHub 도구로 CI 상태를 읽는다.** 그것도
없으면 ❌ 와 함께 "CI 상태를 읽을 수단이 없다"를 남기고 그 노드를 놓는다 —
**읽지 못한 것을 그린으로 처리하지 않는다.**

- 실패하면 원인을 고쳐 다시 민다. **상한 5회 / 60분** — 초과하면 ❌ + 마지막 실패 요약을
  답글로 남기고 그 노드를 놓는다(PR 은 열어 둔다).
- **그린으로 인정하지 않는 것 셋**: 가드 우회 · 테스트 약화(단언 삭제·skip) ·
  **상태를 못 읽은 채 통과 처리.** 통과시키는 것이 목적이 아니라 **맞게 만드는 것**이 목적이다.
- 정책 파일이 요구하는 리뷰어 에이전트가 있으면 PR 을 열기 전에 돌린다(예: 웹 화면 변경 시
  design-reviewer). 리뷰어가 막으면 고치고 다시 본다.

## 6. 절대 규칙

- **▶️·🚀 를 붙이지 않는다.** 사람 전용이고 `bin/mark.py` 가 코드로 막는다.
- **병합하지 않는다.** `pr-merge` 를 부르지 않는다 — 5단계의 일이다.
- **대상 레포의 기본 브랜치에 직접 밀지 않는다.** 자동화의 변경은 전부 PR 을 지난다.
- 엔진 레포(slack-autopilot)를 이 루틴이 수정하지 않는다.
- 스코프를 넓히지 않는다. 불릿에 적힌 것만 한다 — "겸사겸사"가 리뷰를 불가능하게 만든다.

## 7. 시키는 대로가 아니라 **맞게** 만든다 (범위 안에서)

불릿은 **무엇을**만 정한다. **어떻게**는 네가 판단하고, 그 판단은 눈에 보이게 남긴다.

- **원인을 먼저 찾는다.** 증상을 지우는 수정과 원인을 고치는 수정은 다르다. 실례(2026-08-14):
  "초대 링크가 안 보인다"의 원인은 링크가 없어서가 아니라 **CTA 가 카드의 로컬 상태라
  새로고침하면 사라지는 것**이었다. 버튼을 하나 더 놓는 대신 서버가 판정을 알려주게 고쳤다.
- **판정·조건을 복제하지 않는다.** 같은 규칙이 두 곳에 있으면 언젠가 어긋나고, 그 어긋남은
  조용하다. 위 사례에서 발송 게이트와 화면 조건을 각각 짰다면 "눌러도 실패하는 버튼"이 됐다 —
  **같은 함수를 부르게** 했다.
- **재발 방지를 같은 PR 에.** 고친 것이 규칙이면 테스트로 고정한다. 사람이 다시 겪지 않아야
  고친 것이다.
- 다만 **이것은 구현 판단까지다.** "이 기능 자체를 이렇게 바꾸면 어떨까"는 제품 결정이고 B 다
  (D-007 ④). 고치다 그 경계에 닿으면 멈추고 판단 지점을 남긴다.
